#### 2. Core Implementation Steps
4-1. MachineConfigPool (MCP) Creation
Create isolated worker pools optimized for specific network functions.
```
oc apply -f - <<EOF
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-cnf
spec:
  machineConfigSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: worker-cnf
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-cnf: ""
EOF
```

4-2 & 4-3. Kernel Module Loading (SCTP & xt_CHECKSUM)

```
oc apply -f - <<EOF
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-worker-cnf-kernel-modules
  labels:
    machineconfiguration.openshift.io/role: worker-cnf
spec:
  config:
    ignition:
      version: 3.2.0
    storage:
      files:
      - path: /etc/modules-load.d/cnf-modules.conf
        mode: 0644
        contents:
          source: data:,sctp%0Axt_CHECKSUM
EOF
```


4-8. Performance Profile Creation (for cUPF-PP)
  High-throughput user plane pods (cUPF-PP) require dedicated CPU pinning, isolation, and hugepages.
```
oc apply -f - <<EOF
apiVersion: performance.openshift.io/v2
kind: PerformanceProfile
metadata:
  name: performance-profile-upf
spec:
  cpu:
    isolated: "4-31"
    reserved: "0-3"
  hugepages:
    defaultSize: "1G"
    pages:
    - count: 16
      size: "1G"
      node: 0
  nodeSelector:
    node-role.kubernetes.io/worker-cnf: ""
EOF
```

4-10. Samsung SCC (Security Context Constraints) Creation
Apply specialized security permissions for telecommunications container workloads requiring raw socket access or custom capabilities.
```
oc apply -f - <<EOF
apiVersion: security.openshift.io/v1
kind: SecurityContextConstraints
metadata:
  name: samsung-cnf-scc
allowPrivilegedContainer: true
runAsUser:
  type: RunAsAny
seLinuxContext:
  type: RunAsAny
fsGroup:
  type: RunAsAny
volumes:
  - '*'
EOF
```



#### 1. CNF Provisioning Overview & Architecture
Cloud-Native Network Functions (such as 5G Core user-plane or control-plane workloads like UPF/SMF) require specialized handling, high-performance network attachments (via Multus/SR-IOV), customized security context constraints (SCC), and non-root execution frameworks.

```
+-------------------------------------------------------------+
|               OpenShift Cluster Environment                 |
|                                                             |
|   +---------------------+         +---------------------+   |
|   |   CNF Operator      | ------->| Custom CRDs         |   |
|   | (Lifecycle Manager) |         | (UPF / SMF / AMF)   |   |
|   +---------------------+         +---------------------+   |
|              ^                               |              |
|              | GitOps / Helm Deployment      v              |
|   +---------------------+         +---------------------+   |
|   | Multus CNI Network  |         | SR-IOV Data Plane   |   |
|   | (Multi-homing)      |         | (Low-Latency VFs)   |   |
|   +---------------------+         +---------------------+   |
+-------------------------------------------------------------+
```

#### 2. Prerequisites & Namespace Setup

Before deploying CNF workloads, ensure the target namespace is established and configured with appropriate security context constraints (SCC) permissions.
```
# Create dedicated namespace for the CNF workload
oc create namespace cnf-core-system

# Grant necessary permissions for non-root execution and privileged network access if required
oc adm policy add-scc-to-user restricted-v2 -z default -n cnf-core-system
```

#### 3. CNF Operator Deployment via Helm or GitOps
CNF packages are typically structured as Helm charts or custom operator bundles managed via OpenShift GitOps or Helm commands.

3.1 Adding Helm Repositories & Installing CNF Charts

```
# Add the internal or vendor-specific chart repository
helm repo add cnf-charts https://charts.enterprise.samsung.com/cnf
helm repo update

# Install the CNF release package with custom values
helm install core-cnf-release cnf-charts/5g-core-cnf \
  --namespace cnf-core-system \
  --values values-production.yaml
```

#### 4. Configuring Multi-Network Attachments (Multus CNI)
Telco workloads require multiple network interfaces (e.g., O&M, Control Plane, and User Plane data paths). Multus attaches these secondary interfaces to the CNF pods.
```
oc apply -f - <<EOF
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: cnf-dataplane-net
  namespace: cnf-core-system
spec:
  config: '{
    "cniVersion": "0.3.1",
    "type": "sriov",
    "master": "eth1",
    "ipam": {
      "type": "host-local",
      "subnet": "10.244.100.0/24",
      "routes": [{"dst": "0.0.0.0/0"}]
    }
  }'
EOF
```

#### 5. CNF Workload Health and Telemetry Validation
After provisioning, verify that all pods, statefulsets, and network attachments are running correctly and reporting metrics to the observability stack.
```
# Check pod deployment status across namespaces
oc get pods -n cnf-core-system -owide

# Verify network attachment definitions are bound correctly to pods
oc get network-attachment-definitions -n cnf-core-system

# Check streaming logs from the deployed CNF components
oc logs -l app.kubernetes.io/name=5g-core-cnf -n cnf-core-system --tail=100
```
